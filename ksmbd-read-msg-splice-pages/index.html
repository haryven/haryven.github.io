ksmbd 如何减少 SMB2 READ 发送路径上的数据拷贝

发表于 2026-11-24 更新于 2026-11-25 分类于 Linux 内核
以一次 1 MiB 的 SMB2 READ 为例，分析 ksmbd 如何用 MSG_SPLICE_PAGES 发送文件数据，以及 TCP 一次发不完时发送队列如何保留数据页。

中文 · English

在 ksmbd 原来的 SMB2 READ 发送路径上，即便文件已经命中页缓存，1 MiB 的读响应在发给客户端前仍要经历两次内存拷贝；高并发下如果 TCP 发送缓冲区打满、响应被迫排队，未发完的部分甚至还要多拷一次。针对直接发送和排队发送这两条路径，我们向 linux-cifs 提交了两个补丁：用 MSG_SPLICE_PAGES 把数据页直接交给 TCP，并让发送队列直接保留未发送页的引用。在 4 通道、1 MiB 顺序读测试中，吞吐从 6660 提升到 8255.6 MiB/s，宿主机每传输 1 GiB 数据消耗的 CPU 周期下降了 55%。

一、一次 READ 响应里的数据拷贝

以命中页缓存的 1 MiB 顺序读为例，ksmbd 首先通过 kernel_read() 把文件数据从页缓存拷到自己的 aux_payload_buf。接下来还会发生几次拷贝，取决于 TCP 能不能立刻接下这个响应：

如果发送路径空闲，ksmbd 会直接调用 kernel_sendmsg()，TCP 协议栈把数据从 aux_payload_buf 拷进 skb，算上读文件一共是两次拷贝。但如果队列里还有上一个没发完的响应，或者这次 kernel_sendmsg() 只发出去一部分，ksmbd 就得把剩余数据先拷进发送队列的 tcp_tx->data；等后台的 ksmbd_tcp_tx_work 再次发送时，TCP 还要再把这部分数据拷进 skb。这一趟下来，进入队列的数据总共要拷三次。

        PC2["Page Cache"] -->|"拷贝 1: kernel_read"| BUF2["folio / vmalloc 页"]
        BUF2 -->|"快路径: MSG_SPLICE_PAGES 移交页引用"| SKB2["TCP skb"]
        BUF2 -->|"慢路径: folio_get 保留页引用"| Q2["tcp_tx->bvec 队列"]
        Q2 -->|"worker: MSG_SPLICE_PAGES"| SKB2
    end

这次的两个补丁都保留了 kernel_read() 的第一次拷贝：Patch 1 打通直接发送路径，让 TCP 直接引用 READ 缓冲区的物理页；Patch 2 把这套机制延伸到发送队列，让未发完的数据继续留在原页上，等 TCP 有空间时再接着发。

二、为什么不能直接加上 MSG_SPLICE_PAGES？

普通 sendmsg 会把数据逐字节拷进 TCP 自己的发送缓冲区，而带上 MSG_SPLICE_PAGES 后，TCP 可以直接把载荷所在的物理页挂到 skb 上，并通过 get_page() 增加页引用计数。这样一来，ksmbd 在发送调用返回后就能立刻释放自己的引用，TCP 持有的那份引用则会一直保留到网卡发完并释放 skb 时再归还，整个过程不需要拷贝载荷，也不会出现释放后访问的问题。

但这套机制对内存来源有前提：TCP 必须在 ksmbd 释放缓冲区之后仍能安全地持有这一页，内核用 sendpage_ok(page) 来做这项检查。ksmbd 原先用来存响应头和载荷的内存，并不都满足这个条件：

内存来源 底层机制 能否 MSG_SPLICE_PAGES？ 原因
kzalloc / kmalloc 小对象通常来自 slab，大块分配可能来自伙伴系统 不保证 slab 页上的对象不能按独立页交给 TCP
kvmalloc 先尝试 kmalloc，必要时回退到 vmalloc 不保证 需要区分实际分配来源
folio_alloc 伙伴系统分配的整块连续物理页 可以 原生支持 folio_get() / folio_put()
__vmalloc 物理页映射为连续的虚拟地址 可以 每个底层页都可以单独持有引用
page_frag_alloc 从页中分配片段 可以 片段通过底层页的引用维持生命周期

三、Patch 1：改造直接发送路径

在 ksmbd 里，一个标准的 SMB2 READ 响应由 work->iov[0..2] 三段组成（以读取 1 MiB 为例，总长 1,048,660 字节）：

想让整包响应走一次 MSG_SPLICE_PAGES 发出去，需要同时解决两件事：一是把 1 MiB 载荷放到可 splice 的页里，二是处理好前面那 84 字节位于 slab 中的协议头。

1. 载荷分配：folio_alloc 优先，__vmalloc 兜底

对于走 TCP 的普通明文、非复合 READ 请求，只要读取长度不小于 PAGE_SIZE（4 KiB 页系统下即 4 KiB），smb2_alloc_read_buf() 会按两级策略分配载荷缓冲区：

  1. 优先 folio_alloc(GFP_NOWAIT | __GFP_NOWARN | __GFP_NORETRY, order)：在 4 KiB 页系统上，1 MiB 对应一个 order-8 folio（256 个连续物理页）。它直接使用内核线性映射，既不用建立 vmalloc 页表，也没有 vfree() 带来的跨核 TLB shootdown 开销。
  2. 连续大页拿不到时回退 __vmalloc(size, GFP_KERNEL | __GFP_NORETRY | __GFP_NOWARN)：系统运行久了、物理内存碎片化后，高阶分配可能失败，这时用分散的 4 KiB 物理页拼出虚拟连续内存，依然能同时满足 kernel_read() 和 MSG_SPLICE_PAGES。

在确定这个方案前，我们也试过把 folio_alloc + kernel_read 换成 bio_vec[] + vfs_iter_read，但实测下来读进连续大 folio 更快，所以最终保留了现有的读取方式，只改动缓冲区分配和发送路径。

实际落地时还有两个边界需要兜底。第一个是短读：如果客户端请求读 1 MiB、分配了 1 MiB 的大 folio，结果文件只剩 100 KiB 就到 EOF，把这 100 KiB 直接 splice 给 TCP 会让网络栈在传输期间一直占着整块 1 MiB 物理内存。因此当实际读到的字节数满足 get_order(length) < folio_order(folio) 时，直接回退到拷贝路径，立刻释放大页。第二个是 __vmalloc 的缓存一致性：kernel_read() 通过 vmalloc 虚拟地址写入数据，而 TCP 和网卡随后通过物理页的线性映射读取，在存在缓存别名的 CPU 架构上，发送前需要先调用 flush_kernel_vmap_range() 刷新缓存。

2. 用 page_frag_cache 处理 84 字节协议头

响应前部的 iov[0]（4 字节长度字段）和 iov[1]（80 字节 SMB2 响应头）位于 slab 分配的 response_buf 中，不能直接 splice。如果把协议头和载荷拆成两次发送，每次 READ 都要调两次 sendmsg、抢两次 lock_sock(sk)，对 4 KiB / 64 KiB 这类小包开销太大。

参考 NFSD（net/sunrpc/svcsock.c）的做法，我们在每条 TCP 连接上挂了一个 page_frag_cache。发送时先用 page_frag_alloc() 切出 84 字节，把长度字段和响应头拷进去，再把这 84 字节和后面的 1 MiB 载荷合并成一次带 MSG_SPLICE_PAGES 的 kernel_sendmsg() 交给 TCP。虽然这 84 字节仍要拷贝一次，但省掉了后面 1 MiB 载荷的拷贝，同时也保留了单次加锁发送的优势。

整个直接发送路径的引用计数交接时序如下：

sequenceDiagram
    participant W as smb2_read / ksmbd_work
    participant T as ksmbd_tcp_send
    participant TCP as TCP 协议栈 (skb)

    W->>W: folio_alloc (ref=1) + kernel_read 填充数据
    W->>T: ksmbd_conn_write(work)
    T->>T: page_frag_alloc 分配 84B header (ref=1) 并拷贝头
    T->>TCP: kernel_sendmsg(MSG_SPLICE_PAGES, [header, payload])
    TCP->>TCP: 对 header 和 payload 页执行 get_page (ref=2)
    T->>T: page_frag_free(header) 释放自身引用 (header ref=1)
    T-->>W: 返回成功
    W->>W: ksmbd_free_work_struct -> folio_put (payload ref=1)
    Note over TCP: TCP 释放 skb 时归还持有的页引用

3. Patch 1 实测效果

测试环境为 128 逻辑核 Xeon Gold 6430 宿主机 + 4 vCPU virtio-net 虚拟机，客户端通过 SMB3.1.1 读取 tmpfs（16 并发 fio 顺序读，每任务 QD32）：

Channels I/O 大小 吞吐变化 (MiB/s) 宿主 CPU 周期变化 (Gcycles/GiB)
1 4 KiB 288.3 → 287.5 (-0.3%) 27.347 → 27.850 (+1.8%)
1 64 KiB 1975.3 → 2536.1 (+28.4%) 6.815 → 4.668 (-31.5%)
1 256 KiB 2007.2 → 3228.5 (+60.8%) 7.515 → 4.468 (-40.5%)
1 1 MiB 2058.7 → 3119.9 (+51.5%) 5.446 → 3.646 (-33.1%)
4 64 KiB 4260.4 → 4427.3 (+3.9%) 3.207 → 2.985 (-6.9%)
4 256 KiB 6270.3 → 7026.3 (+12.1%) 3.418 → 1.948 (-43.0%)
4 1 MiB 6660.0 → 7833.2 (+17.6%) 3.879 → 2.347 (-39.5%)

从数据看，载荷越大收益越明显：4 KiB 读的瓶颈主要在协议处理和调度开销，省掉载荷拷贝几乎看不出差异；单通道 256 KiB 的吞吐则直接提升了 60.8%。不过到了 4 通道 1 MiB 的高并发场景，吞吐只涨了 17.6%，宿主 CPU 周期仍有 2.347 Gcycles/GiB。继续排查发送统计后发现，高并发下 TCP 发送缓冲区经常打满，有 16.2% 的响应字节没能走成快路径，而是掉进了发送队列里。

四、Patch 2：把页引用保留到发送队列

有两种情况会让 READ 响应进入 tt->tx_queue：一是队列里已经有尚未发完的响应，新响应必须排在后面保序；二是直接发送只发出去了一部分（short send），剩余部分要入队等后续发送。

棘手之处在于生命周期：ksmbd_tcp_writev() 一旦返回，上层很快就会释放 ksmbd_work 和 READ 缓冲区，但入队的数据可能还在等 TCP 腾出空间。旧实现只能把未发送的数据先拷进 tcp_tx->data[]，等后台 worker 发送时再让 TCP 拷一遍。Patch 2 把这套逻辑改成了由队列项 struct tcp_tx 直接持有未发送数据页的引用，直到整包发完或队列项被清理。

1. struct tcp_tx 的布局与偏移切分

队列项的设计主要围绕三个细节展开：

  1. 零增长的结构体布局：在 64 位布局下，msg_flags 后面原本就有 4 字节对齐空隙（偏移 52..55）。新增的 nr_vecs 和 header_len 各占 2 字节，刚好填进这个空隙，结构体固定部分的大小没有增加。
  2. 按发送偏移切分头和载荷：入队时的 offset 可能还落在协议头里，也可能已经发到载荷中间。因为载荷始终排在最后，只要三行减法就能算出剩余的载荷长度和协议头长度： 比如队列非空、offset = 0 时，head = 84、len = 1 MiB，把 84 字节头拷到 bvec 尾部的内联区，保留整块 1 MiB 载荷页引用；如果已经发了 100 字节（84B 头 + 16B 数据），算出来 head = 0、len = 1,048,560，直接跳过前 16B，不需要再存任何协议头。
  3. 适配单 folio 与 vmalloc，统一在最后加引用：单 folio 只需要 1 个 bvec（bvec_set_virt），vmalloc 则通过 iov_iter_extract_bvecs() 按页拆出物理页数组。所有校验和头拷贝全部完成后，再统一对这些页执行 folio_get()——这样一旦前面出错，释放路径只需要一行 kvfree(msg)，不用处理复杂的局部引用回滚。

2. 为什么把协议头内联在 bvec 后面，而不是复用 tx_frag_cache？

初版其实沿用了快路径的思路：同样从 tx_frag_cache 分配协议头，再把头塞进 bvec[0] 一起 splice。但在代码评审时，我们意识到排队发送和直接发送有一个关键区别——发送队列必须对滞留内存做流控记账，复用 tx_frag_cache 会带来两个问题：

  • 共享页被重复记账：tx_frag_cache 底层是一块 32 KiB 大页。如果按 folio_size(header) 逐项记账，哪怕 32 个响应的 84 字节头共享同一个 32 KiB 页，队列配额也会被扣掉 32 × 32 KiB = 1 MiB，很容易提前触发流控。
  • 小 sk_sndbuf 下空队列也会失败：当 sk_sndbuf <= tx->size 时，总记账值 32 KiB + payload 必然超过队列上限，哪怕队列是空的也会被迫退回拷贝路径。

最终我们把尚未发完的协议头直接拷到 msg->bvec 后面的内联区域，按真实的剩余头长 head 记账。后台 worker 的发送顺序也相应拆成两步：如果还有协议头没发完，先用普通 sock_sendmsg 发出去，并带上 MSG_MORE 提示 TCP 后面还有数据；头发完后，立刻在下一轮循环用 MSG_SPLICE_PAGES 发送载荷页。

flowchart TD
    Start["ksmbd_tcp_tx_work 取队头 msg (单次持锁 budget=16)"] --> CheckMode{"msg->nr_vecs > 0 ?"}
    CheckMode -->|"否 (拷贝模式)"| SendData["普通发送 msg->data + offset"]
    CheckMode -->|"是 (零拷贝模式)"| CheckHdr{"offset < header_len ?"}
    CheckHdr -->|"是 (还有头没发完)"| SendHdr["发送内联 header + MSG_MORE"]
    CheckHdr -->|"否 (头已发完)"| SendSplice["MSG_SPLICE_PAGES 发送 msg->bvec"]

    SendData --> Update["统一更新 msg->offset += ret 和 tx_sent += ret"]
    SendHdr --> Update
    SendSplice --> Update

    Update --> Done{"offset == len ?"}
    Done -->|"是 (整包发完)"| Free["扣减 tx_queued, 出队, folio_put 释放页"]
    Done -->|"否"| HdrDone{"offset == header_len ?"}
    HdrDone -->|"是 (刚发完头)"| Continue["continue 立即续发 payload"]
    HdrDone -->|"否 (TCP 缓冲又满)"| Wait["退出循环, 等 write_space 唤醒"]

3. 队列流控记账与回退边界

遇到慢客户端时，数据页会在发送队列里停留很久，如果只按剩余字节数记账，会低估队列实际占住的物理内存。因此保留页引用时，记账值按 head 加上所有保留 folio 的实际大小来算，一旦超出队列上限 max(sk_sndbuf, pdu_size) 就回退到拷贝路径。

同样地，为了避免少量未发完的“小尾巴”把整块大页钉死在队列里，如果剩余数据不足 PAGE_SIZE，或者满足 get_order(len) < folio_order(folio)，也直接只拷贝剩余部分，尽快释放大页。

4. Patch 2 实测效果（叠加在 Patch 1 之上）

每组优化均与同批次重跑的基线对比（因此不同批次间的基线数值会有小幅波动）：

Channels I/O 大小 吞吐变化 (MiB/s) 宿主 CPU 周期变化 (Gcycles/GiB)
1 256 KiB 3243.4 → 3414.6 (+5.3%) 4.511 → 3.497 (-22.5%)
1 1 MiB 3145.6 → 3435.5 (+9.2%) 3.578 → 2.425 (-32.2%)
4 64 KiB 4337.1 → 4448.3 (+2.6%) 2.977 → 3.000 (+0.8%)
4 1 MiB 7705.3 → 8255.6 (+7.1%) 2.673 → 1.746 (-34.7%)

两步合起来看，4 通道 1 MiB 下队列 worker 的拷贝字节占比从 16.2% 降到了 1.0%，P99 延迟从约 203 ms 降到 105 ms；整体吞吐从 6660 提升到 8255.6 MiB/s（+24%），宿主机每 GiB 的 CPU 周期从 3.879 降到 1.746 Gcycles（-55%）。

五、能否直接发送页缓存里的页？

这两个补丁都还保留了 kernel_read() 从页缓存到 READ 缓冲区的那次拷贝。既然 NFSD 的 nfsd_splice_read 可以直接把文件页缓存里的页交给 TCP，ksmbd 走这条路还能再省多少？

我们在只读挂载的 tmpfs 上复用这两片补丁搭好的传输与队列骨架，做了一组 VFS splice 原型验证（结果见上图右侧斜线柱）：4 通道、1 MiB 顺序读吞吐从 8292 进一步提到 8981 MiB/s（+8.3%），每 GiB 的宿主 CPU 周期也从 1.712 再降到 1.228 Gcycles（-28.3%）。

原型刻意选了只读挂载的 tmpfs，是因为页缓存直发在可写共享上会撞上一个经典难题：TCP 持有页引用只能保证这一页不会被回收，却无法阻止并发写入。在可写共享上，如果数据页已经交给了 TCP，但在网卡发出或丢包重传之前，另一个 SMB 客户端或本地进程改写了同一文件页，发出去的字节就会中途变化；开启 SMB 签名时，接收端甚至会直接验签失败。

因此，当前这两个补丁仍然把文件数据读进 ksmbd 私有页，保证对所有可写和只读共享都安全。页缓存直发更适合作为独立方案继续评估——先针对只读挂载的文件系统（sb_rdonly）开启，至于可写共享，还需要理清 SMB Read Lease / Oplock 能约束哪些写入，以及本地进程并发写该如何处理。

六、小结

回过头看这组数据，消除载荷拷贝对较大的 SMB2 READ 请求收益最明显，而在高并发场景下，只改直接发送还远远不够——当 TCP 发送缓冲区频繁打满时，排队路径如何保存剩余数据会立刻成为新的瓶颈，Patch 2 单独就让 4 通道 1 MiB 的宿主 CPU 周期又降了 34.7%。

实现上，把所有边界情况（小包、短读、队列小尾巴、内存超限、加密或压缩）都统一回退到原有的拷贝路径，既避免把零拷贝的复杂度扩散到冷路径里，也能在慢客户端场景下稳住内存上限，整体方案更容易验证，也更好维护。
