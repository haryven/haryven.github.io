ksmbd 读写性能瓶颈分析与优化实践

发表于 2026-10-20 更新于 2026-10-23 分类于 Linux 内核
分析 ksmbd、Samba 与 NFS 的吞吐差异，研究 ksmbd 的读写性能优化方案。

随着 AI 等数据密集型应用的发展，企业对高性能网络文件系统的需求日益增长。在硬件网络带宽与存储性能持续提升的背景下，端到端性能瓶颈可能转移至协议处理、请求调度和数据复制等软件路径。

ksmbd 是 Linux 内核中的 SMB 服务端，为鸿蒙、Windows、Linux、Android、iOS、macOS等平台上的 SMB 客户端提供跨平台文件共享。相较于 Samba 的用户态服务进程 smbd，它在内核态处理 SMB 文件访问请求，有助于减少用户态与内核态切换开销，并通过多核并行处理支撑高吞吐、低延迟访问。

本文从 ksmbd、Samba 与 NFS 的读写性能对比出发，结合内核调用路径和性能采样，分析当前ksmbd的读写性能瓶颈。研究如何通过充分利用CPU、减少读写路径中的数据搬运等方法，提高SMB文件系统的读写性能。

2026-10-22 更新： 本文相关优化已发布 RFC 补丁系列：ksmbd: improve WRITE scheduling and TCP READ sends。完整补丁及社区讨论见该邮件线程。

1. ksmbd、Samba 与 NFS 性能对比

1.1 测试环境与比较范围

测试文件位于 tmpfs 上，以减少块设备延迟的影响。客户端运行在同一宿主机的虚拟机中，通过虚拟网络访问服务端。

项目 配置
物理服务端 双路 NUMA，64 核 / 128 逻辑 CPU
客户端 同机 4-vCPU VM
数据集 tmpfs 容量 8 GiB；工作集合计 1 GiB
fio 并发 16 jobs，每 job QD32，libaio
本文比较的请求大小 64 KiB、1 MiB
负载 顺序 READ、WRITE、50% 读写混合
SMB SMB 3.1.1；1 / 2 / 4 通道；direct=0, cache=none
NFS NFSv4.2/TCP；nconnect=1/2/4；32 个 nfsd 线程
每个样本 15 秒预热 + 2 秒 ramp + 30 秒计量；4 轮

读表约定：

  • 吞吐单位为 MiB/s，取四次运行的中位数；混合为 READ + WRITE。
  • 64K / 1M 是 fio 请求大小，协议层可能拆分请求。
  • SMB 与 NFS 的缓存和完成语义不同；跨协议比较仅提供参考。

2. 请求调度与 workqueue 优化

2.1 从接收线程到 worker

ksmbd 为 TCP 连接创建接收线程，再把完整请求交给 workqueue。worker 负责协议处理、文件访问以及响应的构造和发送。ksmbd 架构文档

flowchart LR
    TCP["TCP 请求"] --> RX["连接接收线程<br/>ksmbd_conn_handler_loop"]
    RX --> Q["ksmbd_queue_request"]
    Q --> W["worker<br/>handle_ksmbd_work"]
    W --> V["SMB 处理 / VFS"]
    V --> TX["连接发送锁<br/>srv_mutex"]
    TX --> SOCK["ksmbd_tcp_writev<br/>TCP 响应"]

默认队列使用：

普通新工作项的执行位置与投递 CPU 相关。接收线程长期停在某个 CPU 时，请求容易集中到对应 pool；迁移后，后续请求又可能落到另一处。

一个 CPU 的 pool 可以有多个 worker；worker 阻塞时，workqueue 可以安排其他 worker 接替。因此，并行度还取决于工作在各 CPU 上的分布，以及处理过程中对共享资源的竞争。workqueue 文档

2.2 CPU/non-strict UNBOUND 的对照实验

一种可行的调整是使用 CPU scope、non-strict 的 WQ_UNBOUND：偏向投递 CPU 执行，同时允许 worker 在偏好范围之外运行。

如果排队主要受执行位置限制，扩大执行范围应当有所帮助。对照测试分别记录了 WQ 排队、发送锁等待和持锁时间：

图 3：PERCPU 与 CPU/non-strict UNBOUND 的阶段耗时。128-CPU 双路服务端，1 job / 1 channel / QD32 / 64 KiB；数值为完整配对请求的平均墙钟时间。

同批不带探针的样本中，READ 从 1933.5 降到 1249.2 MiB/s，WRITE 从 1613.7 升到 1709.1 MiB/s。

两类请求的排队都缩短了，但 READ 吞吐反而下降，发送锁等待也明显增长。直接将全部请求改为 UNBOUND 无法兼顾读写，选择性分流因而成为下一个方案。

2.3 READ 与 WRITE 的发送开销差异

READ 和 WRITE 最终都经过同一个连接发送入口：

  • READ： 响应携带数据，大请求会增加发送阶段的工作量。
  • WRITE： 数据已从接收路径进入服务端，完成响应通常较小。
  • 共同约束： 同一连接的完整帧发送仍然串行，更多 worker 不会消除这个约束。

扩大执行范围可能有助于分散 WRITE 的处理负载，却也可能增加 READ 的发送竞争和跨 CPU 访问成本。一个直接的方案是只将 WRITE 分流到新队列，READ 保留原来的执行方式。

2.4 仅按 READ / WRITE 分流是否足够？

按命令类型分流时，普通 WRITE 交给 U-NS，其余请求保留 PERCPU。纯读、纯写和读写混合的对照结果如下：

单通道负载 分流相对 PERCPU
纯 READ −0.5%
纯 WRITE +6.0%
混合总吞吐 −19.7%

按命令分流版本，1 job / 1 channel / QD32 / 64 KiB，三轮。

纯读基本持平，纯写有所提高，但混合吞吐下降了 19.7%。READ 和 WRITE 即使进入不同队列，仍然共享同一个连接的发送锁。按命令分流并没有消除它们在发送阶段的相互影响。

仅凭当前请求的 opcode，无法判断连接上还有哪些请求尚未完成。因此，分流条件进一步加入连接状态，以限制读写交错时的队列切换。

2.5 加入连接状态，只在 WRITE 阶段分流

改进后的方案保留两个队列，并收紧进入 UNBOUND 的条件。只有符合条件的普通 WRITE 可以分流，其余请求继续使用原 per-CPU 队列。

flowchart TD
    R["接收完整请求"] --> K{"请求分类"}
    K -->|READ / compound / 保护类请求| G["设置连接保护状态"]
    G --> P["原 per-CPU 队列"]
    K -->|普通 WRITE 或本地控制请求| D{"有保护状态且<br/>r_count == 1？"}
    D -->|是| C["解除保护"]
    D -->|否| S{"普通 WRITE、无保护<br/>且未标记多通道？"}
    C --> S
    S -->|是| U["CPU/non-strict UNBOUND"]
    S -->|否| P

图中为开启 WRITE 阶段调度后的简化流程，正常鉴权和协议校验仍在后续路径完成。

这里的 r_count == 1 表示接收线程观察到只剩当前请求的引用。保护机制不会迁移或强行排空已经投递的工作。

  • 根据请求与连接状态选择队列，不实时计算吞吐或调整负载阈值。
  • CPU/non-strict 是局部执行偏好，不保证自动取得最佳 NUMA 放置或始终充分利用空闲 CPU。

这一限制保留了普通单连接 WRITE 使用 UNBOUND 的机会，同时减少混合流量和多通道场景中的放置变化。性能对照见第 4 节。

3.2 通过页引用减少发送复制

普通 READ 先调用 kernel_read() 填充响应缓冲区，再通过 socket 发送。发送时，数据还会从响应缓冲区复制到 TCP 缓冲区。

flowchart LR
    subgraph BEFORE["普通发送"]
        F1["文件系统数据"] -->|"kernel_read：复制"| B1["ksmbd 响应缓冲区"]
        B1 -->|"发送时复制"| T1["TCP 发送缓冲"]
    end
    subgraph AFTER["页支持发送"]
        F2["文件系统数据"] -->|"kernel_read：仍复制"| B2["ksmbd 页支持缓冲区"]
        B2 -->|"MSG_SPLICE_PAGES：引用页"| T2["TCP 发送队列"]
    end

改动针对第二段：为合适的 READ 响应分配可引用页，再通过标准 MSG_SPLICE_PAGES 发送。

kernel_read() 的复制仍在，因此这不是文件页到网卡的端到端零复制。底层不满足 splice 条件时，TCP 也可能回到复制路径。

3.3 页生命周期与报文完整性

TCP 可能在发送调用返回后继续持有数据，实现时需要处理以下约束：

  1. 页有效： TCP 使用期间不能释放、复用或修改数据；响应头也需要可引用页。
  2. 报文完整： 保留整帧发送锁，短发送继续提交，失败时不能拼入下一帧。
  3. 条件受控： 当前只用于符合条件的普通、非 compound、未签名、未加密 TCP READ；失败时回退原路径。

5. 总结

请求调度与数据传输需要结合起来考虑。扩大 workqueue 的执行范围可以为 WRITE 提供更多并行执行机会，但同样的调整未必适合携带大量响应数据的 READ。本文据此保留 READ 的原有调度方式，仅在符合条件的 WRITE 阶段使用 UNBOUND，再通过页支持发送减少 READ 响应进入 TCP 时的复制。

在本文的高并发测试中，两项改动使 1 MiB 单通道读写吞吐分别提升约 57% 和 59%，同时降低了平均完成延迟；1 MiB 四通道 READ 也获得约 22% 的吞吐提升。
目前测试，优化后的ksmbd除了在1M大块写稍微落后nfs，中小块读写场景全面优于nfs。
