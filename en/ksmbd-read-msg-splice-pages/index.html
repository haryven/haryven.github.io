How ksmbd reduces data copies when sending SMB2 READ responses

Posted on 2026-11-24 Edited on 2026-11-25 In Linux 内核

中文 · English

Even on a page-cache hit, ksmbd used to copy a 1 MiB SMB2 READ payload twice before sending it to the client. If the TCP send buffer filled up, the part that had to wait in the queue incurred a third copy. We sent two patches to linux-cifs to address both cases. The first lets TCP reference the data pages through MSG_SPLICE_PAGES. The second lets the send queue hold references to those same pages until TCP can take them. In our four-channel sequential read test with 1 MiB requests, throughput rose from 6660 to 8255.6 MiB/s and the host spent 55% fewer CPU cycles per GiB transferred.

Where the copies happen

Consider a 1 MiB sequential read served from the page cache. First, kernel_read() copies the file data into ksmbd’s aux_payload_buf. What happens next depends on whether TCP can accept the response immediately.

If the send path is idle, ksmbd calls kernel_sendmsg() and TCP copies the payload into an skb. That makes two copies, including the file read. If an earlier response is still queued, or the send call accepts only part of this response, ksmbd copies the outstanding bytes into tcp_tx->data. Later, when the worker ksmbd_tcp_tx_work sends them, TCP copies those bytes into an skb. The queued portion has now been copied three times.

Both patches keep the first copy in kernel_read(). Patch 1 changes how TCP takes the pages on a direct send. Patch 2 extends that lifetime across a queue wait.

Which buffers can TCP reference?

With an ordinary send, TCP copies the payload into its own send buffer. With MSG_SPLICE_PAGES, it can attach the payload pages to the skb and take page references. Once the send returns, ksmbd can drop its own references to the accepted data. TCP releases the references it holds when the skb is freed.

This requires memory whose lifetime TCP can manage through page references. The kernel checks page eligibility with sendpage_ok(page). Some of the buffers ksmbd used for headers and payloads lack that guarantee.

Allocation Backing memory Suitable for page splicing?
kzalloc / kmalloc Small objects usually come from a slab. Large allocations may come from the buddy allocator. Depends on the backing memory. TCP cannot retain a slab object by taking a reference to its containing page.
kvmalloc Tries kmalloc first and can fall back to vmalloc. Depends on which allocation succeeded.
folio_alloc Physically contiguous pages from the buddy allocator Yes. The folio supports folio_get() and folio_put().
__vmalloc Individual pages mapped into a contiguous virtual range Yes. Each backing page can be referenced separately.
page_frag_alloc Fragments allocated from a backing page Yes. A reference to the backing page keeps the fragment alive.

Patch 1. Sending directly from the READ buffer

A regular 1 MiB SMB2 READ response occupies three entries in work->iov[0..2] and totals 1,048,660 bytes. To submit all three entries in one call, ksmbd needs spliceable pages for both the 1 MiB payload and the 84 bytes preceding it.

Allocating the payload

For an eligible plaintext, non-compound READ over TCP, smb2_alloc_read_buf() uses the following allocation order when the request is at least PAGE_SIZE (4 KiB on the test system).

  1. Try folio_alloc(GFP_NOWAIT | __GFP_NOWARN | __GFP_NORETRY, order). On a system with 4 KiB pages, a 1 MiB buffer fits in an order-8 folio of 256 contiguous pages. The kernel can use its linear mapping, avoiding vmalloc page tables and the cross-CPU TLB invalidation that freeing a vmalloc mapping can require.
  2. If the high-order allocation fails, use __vmalloc(size, GFP_KERNEL | __GFP_NORETRY | __GFP_NOWARN). Even when physical memory is fragmented, the backing pages can form a contiguous virtual buffer for kernel_read(), and TCP can reference them individually.

We also tried replacing folio_alloc + kernel_read with bio_vec[] + vfs_iter_read. Reading into a contiguous folio was faster in our tests, so we kept the read operation and changed the allocation and send paths.

Two details matter here. First, a short read near EOF may fill only 100 KiB of a 1 MiB folio. Splicing those bytes would keep the entire folio alive during transmission. When get_order(length) < folio_order(folio), ksmbd falls back to copying and can release the large folio earlier. Second, kernel_read() writes through the vmalloc address, while the subsequent send uses the backing pages. On architectures with cache aliasing, flush_kernel_vmap_range() makes the writes visible before the send.

Handling the 84-byte header

The 4-byte length field in iov[0] and the 80-byte SMB2 response header in iov[1] live in a slab-allocated response_buf. Splitting the header and payload into separate sends would mean two calls to sendmsg and two acquisitions of the socket lock per READ. That overhead matters more for small requests such as 4 KiB and 64 KiB.

Following NFSD’s approach in net/sunrpc/svcsock.c, we keep a page_frag_cache on each TCP connection. For each response, page_frag_alloc() supplies an 84-byte fragment. We copy the length field and header there, then pass the fragment and the payload to TCP in one kernel_sendmsg() with MSG_SPLICE_PAGES. The header still costs an 84-byte copy. The 1 MiB payload can go through in the same call without a second copy.

    participant W as smb2_read / ksmbd_work
    participant T as ksmbd_tcp_send
    participant TCP as TCP stack (skb)
    W->>W: Allocate folio and fill it with kernel_read

The send counters pointed to the queue: under load, the TCP send buffer frequently filled up, and 16.2% of response bytes went through the queue.

Patch 2. Keeping page references in the send queue

A response enters tt->tx_queue when an older response is waiting and send order must be preserved, or when a direct send accepts only a prefix and leaves a suffix to send later.

The request and the queue entry have different lifetimes. Once ksmbd_tcp_writev() returns, the caller can free ksmbd_work and its READ buffer while the queue is still waiting for TCP. The previous implementation copied the outstanding bytes into tcp_tx->data[], then TCP copied them again when the worker ran. With Patch 2, the queue entry, struct tcp_tx, holds references to the unsent data pages until the response is sent or the entry is cleaned up.

Recording what remains after a short send

Structure layout. In the 64-bit layout shown above, there are four bytes of alignment padding after msg_flags, at offsets 52–55. The new fields nr_vecs and header_len take two bytes each and fit in that gap. The fixed portion of the structure stays the same size.

Splitting the remaining bytes. The send offset can fall inside the header or partway through the payload. Because the payload comes last, the worker can calculate the split from the unsent length:

If an earlier response is queued and offset = 0, then head = 84 and len = 1 MiB. The queue saves the 84-byte header inline after the bvec array and references the full payload. If 100 bytes have already been sent, those include the 84-byte header and 16 bytes of payload. Now head = 0 and len = 1,048,560. The queue skips the first 16 payload bytes and stores no header.

Taking references. A single folio needs one bvec, set up with bvec_set_virt. For a vmalloc buffer, iov_iter_extract_bvecs() builds the vectors from its backing pages. The code calls folio_get() only after validation and the header copy succeed. An earlier error can therefore be handled with kvfree(msg), without tracking a partially acquired set of references.

Why store the queued header inline?

Our first version also allocated the queued header from tx_frag_cache and spliced it together with the payload in bvec[0]. During review, we found two problems with charging the queue for the memory it retained.

  • One page could be charged many times. Suppose 32 responses place their 84-byte headers in the same 32 KiB backing page. Charging folio_size(header) per entry consumes 1 MiB of queue allowance for that single page and can trigger flow control early.
  • Even an empty queue could reject the entry. With sk_sndbuf <= tx->size, charging 32 KiB for the header plus the payload can exceed the queue limit on the first entry and force a copy.

The final version copies the unsent header bytes inline after msg->bvec and charges their actual length, head. If any header remains, the worker sends it with ordinary sock_sendmsg and MSG_MORE to tell TCP that more data follows. As soon as the header is complete, the next iteration splices the payload pages.

Bounding the memory held by the queue

A slow client can keep data pages queued for some time. Charging only for the unsent bytes would underestimate the physical memory the queue keeps alive. A page-backed entry is charged for head plus the full size of each retained folio. If the charge exceeds max(sk_sndbuf, pdu_size), ksmbd falls back to copying.

Likewise, a small unsent suffix should not pin an entire large folio. If fewer than PAGE_SIZE bytes remain, or get_order(len) < folio_order(folio), ksmbd copies the suffix so it can release the folio sooner.

Across the two patches, in the four-channel 1 MiB test, the fraction of bytes copied by the queue worker fell from 16.2% to 1.0%, and P99 latency fell from about 203 ms to 105 ms. Throughput rose from 6660 to 8255.6 MiB/s (+24%) and host CPU cost fell from 3.879 to 1.746 Gcycles/GiB (−55%).

Could TCP send the page-cache pages directly?

Both patches still use kernel_read() to copy from the page cache into a private READ buffer. NFSD can hand file pages directly to TCP through nfsd_splice_read. How much would ksmbd gain from a similar read path?

We tried a VFS splice prototype on a read-only tmpfs mount, reusing the transport and queue changes. The hatched bars on the right of the figure show the results. With four channels and 1 MiB sequential reads, throughput rose from 8292 to 8981 MiB/s (+8.3%). Host CPU cost fell from 1.712 to 1.228 Gcycles/GiB (−28.3%).

The read-only mount matters because a page reference keeps a page alive while allowing its contents to change. On a writable share, another SMB client or a local process could overwrite the file page after TCP takes a reference and before transmission or retransmission. The transmitted bytes could then differ from the bytes ksmbd originally read. If the response was signed, signature verification could fail at the receiver.

The two proposed patches keep a private copy of the file data, which avoids this race on writable as well as read-only shares. Direct page-cache sends can be evaluated separately, starting with read-only filesystems (sb_rdonly). Extending the approach to writable shares requires accounting for what SMB read leases and oplocks can protect, including what happens when a local process writes to the file.

What the measurements show

Larger SMB2 READ requests benefited most from eliminating payload copies. Under concurrency, the queue mattered even after the direct path could splice pages. Once the TCP send buffer filled up, the way ksmbd kept the outstanding bytes determined whether it had to pay for those copies again. In the four-channel 1 MiB test, Patch 2 alone reduced host CPU cycles per GiB by another 34.7% relative to Patch 1 in the same batch.

Small requests, short reads that would pin oversized folios, small queued suffixes, entries over the memory limit, and encrypted or compressed responses can all use the existing copy path. That keeps page handling confined to eligible sends and bounds the memory a slow client can retain.
